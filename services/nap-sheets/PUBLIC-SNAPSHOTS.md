# Public NAP dashboard and Chopping Block integration

The user authorized public NAP and NAPCont records, including existing notes. `data/nap.json` is the normalized daily snapshot; `incidents.html` reads it without an access key, Apps Script or server. Raw displayed cells/backgrounds remain backed up in the private scanner repository on data/nap-snapshots. Daily scheduled maintenance publishes the normalized public copy using `node scripts/publish_nap_snapshot.cjs PRIVATE_INPUT PUBLIC_OUTPUT`; it must preserve popup screenshot privacy.

`nap-model.js` builds an index from server-125 passive world-map records: dated current names, `player_history_json` username observations and `name_history_json` rename boundary observations. Untimed aliases alone never establish a match. It first compares exact normalized spelling/case, within an incident's game UTC−2 date interval. The candidate with the smallest distance in whole days wins; equal distances remain ambiguous. Both past and subsequent observations can be candidates, so all matches are labelled nearest-history estimates with their observation gap, not confirmed identities. Sparse scan history cannot prove who owned a name on an earlier date.

Both aggressor and victim IDs are resolved. Chopping Block associates those stable IDs with the current observed D3AD roster, including members who renamed since the incident. Incidents involving a current member in a previous guild still appear. Unmatched names, unknown dates and ties remain unlinked; no current-alias fallback silently resolves them. The page displays reported-role counts and expandable context; no incident changes the contribution score or establishes a confirmed violation. Column G/authorization text remain uninterpreted. Summary totals are excluded; identical source rows retain their review warning.

Team corrections remain in the original Sheet. Failed source reads leave the last successful public snapshot available with its original timestamp. There is no write form or automatic punishment policy in this read-only integration. The previous optional private Apps Script/WSGI adapters remain source examples but are not needed for this public view.

## Fuzzy fallback

Only absent exact-history names can use fuzzy matching. Existing exact matches or ambiguous exact IDs are never replaced. Query names must have 5–80 Unicode code points and candidates 4–80; digit sequences must match exactly. Adjacent letter transpositions count as one edit. Short names allow at most one edit and 80% similarity; names at least 12 characters allow up to two edits with at least 85% similarity. Candidates need a dated observation within 30 days of the incident date.

Aliases are grouped by stable player ID before comparison. The winning ID must beat the next eligible ID by at least ten similarity percentage points, otherwise it stays unresolved. The date selects the closest observation within a candidate, but cannot override an unclear spelling match. Both pages label fuzzy links with similarity, matched spelling and observation gap. These heuristics do not establish identity or trigger score deductions; sparse history and common names can still need manual review.
